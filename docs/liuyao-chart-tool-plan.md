# 六爻排盘与档案工具：产品及技术实施计划（技术研究输入）

> 定位说明（2026-08-06）：本文保留前期服务端方案作为历史研究输入，运行时架构已由 DEC-038 改为完全离线 Flutter + 纯 Dart 引擎。当前事实源见 [离线 Dart 架构](./architecture/offline-dart-architecture.md)、[文档中心](./README.md) 和各功能 Spec。

> 状态：待确认后实施  
> 当前范围：先做独立排盘与档案工具，不做 Agent、模型解读或对话能力  
> 历史技术基线：Flutter + Node + Python（已被 DEC-038 取代）

## 1. 项目目标

先建立一个结果稳定、过程可核验、档案可长期保存的六爻排盘工具。后续 Agent 只能消费这个工具提供的同一份盘面与档案数据，不能另算一套盘、另存一套业务数据。

第一阶段完成后，用户应能：

1. 使用“自动铜钱”或“手动录入”完成起卦。
2. 查看本卦、变卦、六亲、六神、世应、动爻、纳甲、伏神等基础盘面。
3. 在卦面下展开查看每一项结果的完整计算过程，而不只看到结论。
4. 保存卦例，分别编辑“解读”和“反馈”，并保留修改历史。
5. 选择一个或多个档案，一键导出盘面、解读和反馈数据。
6. 后续逐步增加神煞、十二长生、五星二十八宿入卦及建候积算。

## 2. 本期明确不做

- 不接入 Pi Agent SDK、LLM、Prompt、知识检索或聊天页面。
- 不生成带主观判断的“吉凶评分”或 AI 解读。
- 不把 Taoracle 的 `prompt_assembler.py`、`context_builder.py` 等 Agent 层代码带入基础工具。
- 不在第一期同时实现所有流派的神煞、长生和星宿规则；这些必须先确认口径并建立固定样例。

## 3. 现有项目审阅结论

### 3.1 已有能力

| 能力 | 当前状态 | 结论 |

| 手动排盘 | 已支持按初爻到上爻录入 6/7/8/9 | 可直接作为第一期入口 |
| 纳甲排盘 | 已通过 `najia==2.0.1` 得到卦名、卦宫、纳甲、六亲、六神、世应、伏神、变卦 | 可复用并需要加合同层校验 |
| 档案 | 已有 SQLite 案例、列表、详情和分析版本表 | 可迁移为非 Agent 的案例 API |
| 移动端 | 已有新建、列表、详情、盘面和分析编辑骨架 | 可复用并重新组织信息层级 |
| 导出 | 未实现 | 新增 |
| 反馈 | 未单独建模 | 新增，不能与解读混为一张表 |
| 神煞 | 未实现 | 后续独立规则包 |
| 十二长生 | 仅 Taoracle 分析器中存在“墓”的简化判断 | 不可视为完整实现 |
| 五星二十八宿、建候积算 | 未实现 | 后续按《京氏易传》口径专项实现 |

### 3.2 可复用代码边界

可以复用：

- 当前 `services/liuyao-engine/app/engine.py` 的 `Najia.compile` 适配思路。
- Taoracle `najia_adapter.py` 中的卦宫、六亲、六神、世应、伏神和变卦合同转换思路。
- 当前 `CaseService`、SQLite Repository、Flutter 档案页的骨架。

需要拆解后再用：

- Taoracle `technical_analyzer.py` 中的月建、日辰、旬空、合冲、动变、伏神等判断可以作为规则需求清单，但不能原样成为基础盘面算法。
- 原因是该文件包含人为分值、吉凶措辞和“简化版三合”等分析性规则；基础盘必须输出可验证的事实和推导，不能把某套权重伪装成通用规则。

不复用：

- Taoracle 的 AI 调用、Prompt、知识选择、话题分类和咨询流程。

### 3.3 当前合同需要优先修正的问题

1. `raw_najia.qinx` 的值类似 `戊寅木`。当前合同把前两个字整体放进 `branch`，实际这是“天干 + 地支”。新合同应明确拆成 `stem=戊`、`branch=寅`、`element=木`、`najia=戊寅木`。
2. 当前自动起卦只保存每爻合计，没有保存三枚铜钱的逐枚结果，无法完整复盘计算。
3. 当前只保存 UTC offset，没有保存 IANA 时区名称；在跨时区、夏令时和节气边界附近不够稳妥。
4. `raw_najia` 适合审计和迁移兜底，不应成为移动端长期依赖的展示合同。
5. 当前“分析”表混有 `user/agent` 作者概念；本期应改成明确的“解读版本”和“反馈版本”。

## 4. 产品信息架构

### 4.1 主导航

- 排盘：新起一卦，支持自动与手动模式。
- 档案：搜索、筛选、批量选择、查看、编辑、导出。
- 设置：默认时区、排盘规则版本、扩展标注开关、导出选项。

本期移除或隐藏“助手”入口和所有 Agent 文案。

### 4.2 自动模式

自动模式按三枚铜钱法连续生成六爻，顺序固定为初爻到上爻。每爻必须保存并显示：

- 三枚铜钱逐枚结果及其数值。
- 求和过程，例如 `3 + 2 + 3 = 8`。
- 6/7/8/9 对应的老阴、少阳、少阴、老阳。
- 阴阳、是否动爻，以及变爻后的阴阳。
- 随机源类型；测试环境允许 seed，正式用户档案默认不暴露或依赖 seed。

界面可一次生成整卦，但详情中必须能展开看到六次投掷过程。以后可增加逐爻投掷动画，不阻塞基础版。

### 4.3 手动模式

手动模式第一期使用 6/7/8/9 录入，顺序明确显示“初爻 → 上爻”。每个数字同时显示名称和爻象，提交前显示整卦预览，避免上下顺序录反。

手动录入仍需要生成相同的计算轨迹，只是轨迹来源标为 `manual_input`，铜钱明细为空。

### 4.4 盘面展示

主盘面保持紧凑，默认显示：

- 起卦时间、时区、四柱、旬空。
- 本卦、卦宫、宫五行、世应、动爻、变卦。
- 每爻：爻位、六神、伏神、六亲、纳甲干支五行、阴阳爻、动变标记、世应。
- 变卦每爻对应的纳甲、六亲和阴阳。

盘面下方设置分层抽屉，避免高级信息把主盘挤乱：

1. 起卦过程。
2. 基础排盘推导。
3. 日月、旬空与关系标注。
4. 神煞与十二长生。
5. 五星二十八宿、建候积算。
6. 原始数据与规则版本。

## 5. “所有运算情况”怎样落地

所有派生结果都不能只返回一个字符串结论。引擎为每个计算步骤输出结构化 `calculation_trace`：

```json
{
  "rule_id": "six_gods.by_day_stem.v1",
  "label": "六神起法",
  "scope": "chart",
  "inputs": {"day_stem": "辛"},
  "lookup": {"start_god_at_first_line": "白虎"},
  "steps": ["初爻起白虎", "按初爻至上爻顺排六神"],
  "result": ["白虎", "玄武", "青龙", "朱雀", "勾陈", "螣蛇"],
  "source_id": "rulebook.six_gods.v1",
  "rule_version": "1.0.0"
}
```

统一要求：

- 每条轨迹都有规则 ID、输入、查表值、中间步骤、结果、来源和版本。
- 盘级规则与爻级规则分开；爻级规则必须带 `line_position`。
- 界面显示人可读推导，导出文件保留完整结构化轨迹。
- 规则升级不改写旧档案；旧档案继续保留当时的 `engine_version`、`schema_version` 和 `rule_set_version`。
- “事实排盘”“辅助标注”“主观解读”三层数据严格分开。

首批必须可追踪的规则：

- 铜钱值 → 爻值 → 阴阳/动静 → 变爻。
- 六爻阴阳组合 → 本卦名。
- 动爻翻转 → 变卦名。
- 八宫归属、宫五行、世应定位。
- 纳甲干支、爻五行、六亲。
- 日干起六神及逐爻排布。
- 本宫纯卦六亲缺失 → 伏神所在爻位。
- 年月日时干支与旬空的来源。

## 6. 建议的数据合同 v2

### 6.1 排盘快照

```text
ChartSnapshotV2
├── schemaVersion / engineVersion / ruleSetVersion
├── input
│   ├── question / title
│   ├── castAt / timezoneId / utcOffset
│   ├── method
│   └── lines[]
│       ├── source
│       ├── coins[]
│       └── value
├── calendar
│   ├── solar / lunar
│   ├── yearGz / monthGz / dayGz / hourGz
│   └── dayVoid
├── hexagrams
│   ├── base
│   └── changed
├── annotations
│   ├── shensha
│   ├── twelveStages
│   └── jingfangStarsAndAccumulation
├── calculationTrace[]
└── sourcePayloads
```

每个爻的稳定字段至少包含：

- `position`、`positionName`、`rawValue`、`yinYang`、`changing`。
- `stem`、`branch`、`element`、`najia`。
- `relation`、`sixGod`、`role`。
- `hiddenSpirits[]`，使用数组而不是单个可空对象，给未来规则扩展留余地。
- `changedLine` 对应信息。

### 6.2 档案模型

- `cases`：标题、占问事项、起卦输入、不可变盘面快照、创建和更新时间。
- `interpretation_revisions`：用户解读正文、版本号、创建时间。
- `feedback_revisions`：反馈正文、验证状态、验证日期、结果标签、版本号。
- `case_tags`：后续筛选和归档标签。
- `exports` 不必第一期落库，但导出清单内要有生成时间、格式版本和案例校验值。

建议的反馈字段：

- 验证状态：未验证、部分应验、已应验、未应验、无法判断。
- 反馈日期或事情发生日期。
- 实际结果正文。
- 可选的应期、关键对应点和补充备注。

## 7. 导出设计

第一期同时支持两种格式：

1. JSON：完整、可机器读取，包含盘面、轨迹、解读版本、反馈版本和规则版本。
2. Markdown：适合阅读、打印和交给其他工具，包含格式化卦面、计算说明、最新解读、最新反馈；可选择附带历史版本。

交互要求：

- 详情页可导出单个档案。
- 档案列表进入多选模式后可批量导出。
- 批量导出使用一个 ZIP，内含每卦 JSON 和 Markdown，以及总清单 `manifest.json`。
- 导出前允许选择：仅最新解读/反馈，或包含全部历史版本。
- 导出内容不得依赖 Agent 服务或模型凭据。

## 8. 扩展规则路线

### 8.1 神煞

神煞必须采用“白名单规则包”，不追求一次收录所有民间神煞。每个神煞记录：

- 以年干、日干、年支、日支或其他字段中的哪一个为起点。
- 查表过程和命中爻位。
- 同名异法时使用不同 `rule_id`，不暗中混用。
- 默认只做位置标注，不自动判吉凶。

具体首批神煞清单需在实施前确认。

### 8.2 十二长生

“十二长生”存在至少两种会影响结果的实现口径：按五行统一顺行，或按十天干并区分阴阳顺逆。实施前必须明确本工具采用哪套，以及要计算“每爻相对月建”“每爻相对日辰”还是其他关系。

第一版建议同时保留计算对象和参照对象，例如：

```text
本爻：戊寅木
参照：未月
规则：木长生于亥，十二支顺排
步进：亥长生 → 子沐浴 → … → 未墓
结果：墓
```

这类完整步进必须在卦面下展开，不能只写“墓”。

### 8.3 五星二十八宿与建候积算

初步研究表明，该需求应按《京氏易传》的卦气体系理解：每卦涉及世应、建始、积算、气候分数、五星从位起、二十八宿从位降等内容，不等同于黄历的“当日值宿”。

本模块计划输出：

- 当前卦对应的建始起止。
- 积算起止、循环单位和“周而复始”的展开过程。
- 气候分数及其规则来源。
- 五星的起位、当前五星与落位。
- 二十八宿的起宿、顺序、每爻分配及最终落爻。
- 世爻、应爻与纳甲爻位怎样参与计算。
- 原文条目、采用的底本/校勘版本和规则版本。

实现方式不是把古文结论写死在 UI，而是先建立经过审阅的 64 卦规则表，再由引擎进行循环与落位计算。历史文本存在版本差异和疑似讹误，因此必须用用户认可的底本或规则表做 golden fixtures。

## 9. 架构调整

```text
Flutter App
  └── Case API（纯业务 API，不依赖 Agent SDK）
        ├── CaseService
        ├── SQLite Repository
        ├── ExportService
        └── Liuyao Engine Client
              └── Python Rule Engine（无状态、可版本化、可追踪）
```

建议将当前 `services/agent` 拆成或改名为 `services/app-api`。若暂时不重命名目录，也必须先移除运行时的 Pi SDK 初始化、聊天路由和模型配置，使排盘与档案可在没有任何 API Key 的情况下独立运行。

建议的业务接口：

- `POST /api/charts/preview`：排盘但不存档。
- `POST /api/cases`：排盘并建档。
- `GET /api/cases`、`GET /api/cases/:id`。
- `PUT /api/cases/:id/interpretation`：保存解读新版本。
- `PUT /api/cases/:id/feedback`：保存反馈新版本。
- `POST /api/exports`：单个或批量导出。
- 引擎继续使用 `POST /v1/cast`，合同升级到 v2。

## 10. 分阶段实施计划

在规则口径及时确认、由当前代码骨架继续开发的前提下，粗略工作量为：里程碑 0 约 1–2 个工程日，里程碑 1 约 4–6 日，里程碑 2 约 4–6 日，里程碑 3 约 4–7 日，里程碑 4 约 7–12 日，里程碑 5 约 3–5 日。完整范围合计约 23–38 个工程日；五星二十八宿底本的整理与校勘是最大不确定项。各里程碑依次验收，不要求一次全部开工。

### 里程碑 0：规则与合同冻结

产出：

- 确认首期范围和四个规则口径问题。
- 完成 `ChartSnapshotV2` JSON Schema。
- 建立至少 6 个固定时间、固定爻值的人工校验样例，覆盖静卦、单动、多动、六冲/六合、归魂/游魂和伏神。
- 为每个规则登记来源、版本、输入和输出。

验收：同一个输入永远得到相同结果；人工样例能逐字段对上。

### 里程碑 1：纯排盘工具 MVP

产出：

- 从 App 和 API 中移除 Agent 入口与运行依赖。
- 自动/手动排盘流程。
- 基础盘面合同 v2 和计算轨迹。
- 新盘面 UI 及“计算过程”展开区。

验收：无需 API Key 即可从手机完成排盘并看到全部基础推导。

### 里程碑 2：档案、解读、反馈与导出

产出：

- 档案搜索、详情和批量选择。
- 解读与反馈分开编辑、自动保存或显式保存、版本历史。
- 单个 JSON/Markdown 导出和批量 ZIP 导出。
- 旧 `schema_version=1` 档案兼容读取或一次性迁移。

验收：导出内容与数据库快照一致，离线打开也能完整阅读和核验。

### 里程碑 3：神煞与十二长生

产出：

- 经确认的神煞白名单规则包。
- 十二长生结构化结果与逐步轨迹。
- 盘面标注开关及图例。

验收：每一条标注都能展开看到“输入 → 查表/步进 → 结果”。

### 里程碑 4：五星二十八宿与建候积算

产出：

- 64 卦规则数据表及来源说明。
- 五星、二十八宿、建始、积算和气候计算模块。
- 卦面下的完整积算展示。

验收：选定底本中的代表卦与工具输出逐项一致，且可复算出落爻过程。

### 里程碑 5：完整性与发布加固

产出：

- 覆盖全部 4096 组 `6/7/8/9` 六爻输入的穷举合同测试。
- 64 卦、伏神、世应、动变和时区/节气边界测试。
- Flutter widget、API、SQLite 迁移和导出 round-trip 测试。
- 规则版本升级与旧档案回放测试。

验收：无上下爻顺序错误、无新旧档案漂移、无导出丢字段。

## 11. 质量门槛

- Python 排盘规则变更必须增加固定时间、固定爻值的 golden test。
- 关键映射采用穷举或表驱动测试，不能只测一两个示例。
- TypeScript 保持 strict；Flutter 网络与存储逻辑不进入 Widget。
- 所有爻数组在合同层固定为初爻到上爻，只有 UI 渲染时反转。
- 任何新规则都必须包含 `source_id` 和 `rule_version`。
- 不允许基础引擎直接输出“吉、大吉、凶”等解释性判断；这些属于用户解读或未来分析层。

## 12. 实施前需要确认的四个口径

1. “自动模式”是否确定为电脑模拟三枚铜钱法，并在档案中保存每枚铜钱结果？
2. 首批神煞具体需要哪些；是否先从天乙贵人、禄神、驿马、桃花、文昌、华盖、将星等白名单开始？
3. 十二长生采用“五行十二长生”还是“十天干阴阳顺逆”，以及分别相对月建、日辰显示哪些结果？
4. 五星二十八宿是否确定采用《京氏易传》的入卦、建候、积算体系，而不是黄历值日二十八宿？如已有指定口诀、表格或底本，应以该材料作为唯一验收基准。
